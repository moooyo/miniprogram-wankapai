## New findings

### R13-01 — P2: Keep workbench navigation and scenario completion tied to their initiating owner

At discovery, `prototype/runtime.js` guarded Refresh with `sourceOperationPending`, but atlas, flow and scenario navigation could still call the shared push-navigation path. A leave confirmation allowed this navigation while a source form was saving. Push navigation hid the old instance without unloading it. Its eventual successful completion was therefore still allowed to clear the current native leave warning and call `wx.navigateBack()`.

The issue was confirmed with real rendered controls and the real demo domain service. A Card Edit instance saved a nickname; the command committed, and only delivery of its successful response was held. The reviewer then used the workbench atlas to open Preferences, accepted the Card departure prompt, and changed an unsaved preference. Releasing the old Card response cleared the Preferences leave warning and popped the dirty Preferences instance without a second confirmation. The preference remained unsaved. This is loss of an intervening page's input, not merely an unexpected toast or an inferred risk.

Evidence: `.qa-native/prototype/candidate-r11/r13-busy-navigation-report.json` and its matching `r13-busy-navigation-repro.mjs`. The proof identifies the frozen HTML hash above and records zero runtime exceptions. The reviewer read the complete trace and inspected all four screenshots: `r13-busy-navigation-01-card-saving-committed.png`, `r13-busy-navigation-02-leave-saving-card-confirmation.png`, `r13-busy-navigation-03-preferences-dirty-before-old-response.png`, and `r13-busy-navigation-04-old-response-popped-dirty-preferences.png`.

The trace identifies Card instance 4 and Preferences instance 5. Before response release, Preferences has `dirty: true`, `newActivities: true` and a leave warning. After release, the old callback has cleared that warning, Preferences is disposed while still dirty, no new confirmation appeared, and the stored preference remains false. These assertions directly support the finding.

The corrective source reread also found a remaining scenario-ownership boundary: the pagination fixture unconditionally restored its captured prior role in `finally`. A second remote rendered-control proof on the frozen incoming artifact held the first real pagination `submission.save` response after commit, then entered the moderator-review scenario. Review was ready with `isModerator: true`. Releasing the old pagination response eventually restored the old ordinary-user role; the current Review's next moderation query returned `FORBIDDEN`, and clicking its Published tab displayed the no-permission state. The same unconditional restoration line was present in the first corrective runtime, so guarding further fixture writes alone did not close this boundary.

Evidence for this integration tail: `.qa-native/prototype/incoming-r11/r13-pagination-role-repro.json`, `r13-pagination-role-review-ready-before-release.png` and `r13-pagination-role-review-permission-revoked.png`. The reviewer read the relevant state/command trace and inspected both screenshots. The proof has the same incoming hash and zero runtime exceptions. The older artifact also continued its pagination writes; that older write continuation is not attributed to the partially corrected runtime. The independently verified remaining issue was late restoration overriding a newer selected demo role.

Recommendation: Guard user-operated workbench navigation with the captured source-page owner and pending-operation state before departure, after asynchronous preparation or confirmation, and immediately before committing a destination. Initial form loading and draft-recovery dialogs belong to the same ownership boundary. Blocked or cancelled actions must not change role, inject fixtures, consume scenario mutations, or hide the owner. A temporary fixture role must be released by its own active operation only, without overriding a newer explicit role or remaining enabled after ordinary navigation. Keep native source-driven success navigation and native-style Back/unload behavior intact: a general ban on `wx.navigateBack()` while `saving` is true would also prevent normal successful form completion.

Acceptance: Cover atlas, flow, all scenario entries, `openPage`, public prototype navigation/reset, and asynchronous target resolution. A blocked attempt must preserve route, current instance, input, scroll, warning and stored fixtures. A normal successful save must still return as designed. Cancellation must have no scenario side effects. A delayed fixture must stop affecting a newer scenario; test navigation to a newer explicit moderator role and to an ordinary page. Native Back must retain its established unload/disposal behavior.

### R13-02 — P2: Offer exact same-period receipt recovery after the participation gets an ID

The new round 12 receipt recovery filters correctly reject another card, another period and an unknown target. At discovery, however, `miniprogram/pages/receipt/index.ts` also rejected a known creation draft whenever an explicit participation route was opened and the draft had not been marked as a creation conflict. The pending branch rejected every explicit participation route before comparing its known original target.

A supported same-user flow exposes this distinction: open a first Receipt form, enter an amount/date and leave a normal draft; return to Detail and join that same activity in the same period and user/card scope; then open Receipt through the new participation ID. The exact original draft is filtered out, so the normal route displays default fields without offering recovery. Similarly, if a first receipt actually committed but its response was lost, opening its exact resulting participation ID filters out the pending original-result check. The original storage entry remains, but the ordinary exact-record entry no longer exposes it.

The implementation owner independently reproduced both paths using the real Receipt controller, API and `createService`, in both user and card scopes: four failing regression cases observed zero recovery dialogs where one was required. The tests in `tests/receipt-period-draft.test.ts` are named `an ordinary same-period <scope>-scope creation draft is recoverable after joining and opening the explicit participation` and `an explicit same-period <scope>-scope participation can recover and only look up its committed pending creation`, each for `card` and `user`. These before proofs are controller/API/domain tests; the later corrected candidate separately exercised all four through rendered browser controls.

Recommendation: Permit explicitly confirmed recovery when the saved target and the loaded exact participation have the same activity, scope, card where applicable, and period. A previously absent participation ID must not itself disqualify that exact match. Keep the original uncertain-creation namespace and immutable payload for read-only result resolution. Preserve all exclusions for a different period, different card, mismatched record and unknown target; do not broadly restore generic drafts into arbitrary historical editors.

Acceptance: Cover ordinary pre-join drafts and committed-but-unacknowledged creation drafts, each in user/card scopes, reopened through both activity context and the exact participation ID. Show the original values and require the existing explicit recovery/compare decision. Keep different-card, different-period, unknown-target, stale-version and conflict controls passing. Recovery must neither duplicate a receipt nor consume another target's draft.

### R13-03 — P2: Ask for a target decision when the first-ever receipt save crosses a period

At discovery, a new Receipt form persisted `pendingCreation` before forcing a fresh session/date read. If the activity period had changed while that form remained open, `resolvePendingCreation()` changed that brand-new intent to read-only replay before dispatching any `reward.confirm` command. An absent result then left the form in the same locked state as a genuinely uncertain request. Its inputs could not be edited, target confirmation rejected pending creations, and loading returned early. The message said the original operation might still be processing even though this controller had never sent it.

The implementation owner confirmed the mechanism remotely with the real controller, API and domain service and a controlled clock. A September 30 form retained a September amount/date and was first saved on October 1. The assertion that no `reward.confirm` had been dispatched passed. The subsequent assertion expecting zero `request.replay` calls failed because one lookup had been sent. The precise regression in `tests/receipt-period-draft.test.ts` is `a never-submitted live September receipt becomes an ordinary target-review draft before its first October save`; its before failure occurred at the zero-replay assertion. This is a focused controller/API/domain clock proof, not a physical-device test.

User impact: A legitimate first attempt can enter a recovery state that cannot find an original result and cannot offer the existing explicit period decision. Keeping the money/date safe does not make that dead end usable. It must remain distinct from a request whose delivery or commit is truly unknown.

Recommendation: Before marking an ordinary draft as an uncertain creation, refresh its authoritative target and detect a period change. Preserve the original amount, actual date and target, then expose the existing explicit current-target decision. Do not automatically rewrite the actual date or issue a new current-period command. Only a genuinely dispatched uncertain request should retain immutable original payload/namespace and the read-only original-result path. Keep the server expected-period guard because the calendar can still change between preflight and commit.

Acceptance: Hold an ordinary form open across a month/year boundary before its first save. Neither a write nor a result lookup should occur until the user decides what target to use. After explicit target review, retain the original date so validation can request an appropriate date deliberately. A corrected current-period form should save once. Existing committed and unknown original requests must continue to resolve with their original request identity without duplicate or cross-period execution.
