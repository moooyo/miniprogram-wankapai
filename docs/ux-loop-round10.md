## New actionable findings

### R10-01 — P1: Keep native bundled configuration imports resolvable

Source mechanism: `scripts/build.mjs` marks any `runtime-config` import external by returning the original `args.path`. `services/entrance.ts` imports `../runtime-config` and is bundled into the Detail page. A relative external path originating in the service module was emitted unchanged in `dist/miniprogram/pages/detail/index.js`, where it points at `pages/runtime-config` instead of the Mini Program root configuration.

User impact: The native Detail page cannot initialize because its generated module requires that missing file. The browser prototype uses a separate build plugin that inlines demo configuration, so its passing scenarios do not detect this native-output failure. The local native `dist/` copy was stale and was not used as proof.

Remote confirmation: Before altering the old build or generated package, the implementation reviewer uploaded only the new package checker and ran it on `test-env`. It exited 1 with `Error: Unresolved native dependency: pages/detail/index.js -> ../runtime-config`. The command, original failure, correction, and verification boundary are recorded in `docs/ux-loop-native-package.md`, which the round reviewer read. This is a module-resolution failure in the generated native package, not a claim that a physical device was exercised.

Correction reread: The round reviewer read the revised complete `scripts/build.mjs` and new `scripts/check-native-package.mjs`. Each native entry now resolves shared modules by absolute source identity and emits paths relative to its final output. Metadata asserts that configuration and shared API/privacy remain external and the demo runtime remains only in the API bundle. The remote corrected build, type check, and package check passed for 16 pages, 3 components, 2 services, 1 app and configuration file, totaling 23 modules and 23 literal dependencies. `.qa-native/prototype/candidate-r9/r10-native-resolution.json` independently records corrected Detail and API dependency resolutions. That JSON is post-fix evidence; the earlier failure is the separately documented checker result. No generated output was hand edited. Node registration checks do not render WXML or invoke native lifecycles.

### R10-02 — P2: Preserve unknown-result recovery across date changes

Source mechanism: Card Edit restores the original creation intent and pending payload signature, but its new load uses the current session month. An original due date can then fail `validationErrors()` against the new month's statement date before the unchanged request reaches the idempotent API. The pending-creation exception currently addresses a self-caused nickname collision, but not this date transition. Full Submission likewise restores its intent and original draft while applying `endsOn < today` before dispatch; a submission that succeeded with a lost response on its final day cannot be retried after midnight.

User impact: The user has an existing created record, a retained original draft, and a retry identity, yet the recovery action cannot determine the saved result. The interface asks for date changes even though the intended operation already succeeded, increasing confusion and the chance of an unintended new creation.

Remote confirmation: With browser-only deterministic time and the real source controls/domain, the reviewer created a credit card on September 30 with statement day 5 and a September 30 due date. Persistence and the request-ledger result succeeded, then the response was lost. The exact intent key and pending payload signature were recovered on October 1. Clicking Save produced a due-date error against the October statement date and did not dispatch a second API command. The already-created card remained present. `.qa-native/prototype/candidate-r9/r10-card-date-repro.json`, case `recovered-creation-replay-blocked-after-month-rollover`, records the stored request, original/recovered form values, one-command trace, and validation result. The round reviewer read its relevant checkpoints and inspected `r10-card-date-replay-before-rollover.png` and `r10-card-date-replay-rejected-october.png`.

Recommendation and acceptance: Recovery must distinguish an already committed original operation from a genuinely new or changed expired payload. Retest exact pending Card recovery across a month boundary, changed payloads, and an original request that never committed. Add the source-identified Full Submission end-date boundary to correction acceptance: a committed-but-lost submission must be recoverable after its end date, while a new or changed expired submission remains rejected. Simply bypassing expiry checks for every saved intent is insufficient: the prior submission validator does not independently reject all past end dates. No claim is made that the old Full Submission path was browser-reproduced in this round.

### R10-03 — P2: Bind a card form's bill correction to the period it displayed

Source mechanism: Card Edit loads `currentMonth` and a current-bill `dueOn`, then includes the date in every independent-billing save, even when only the nickname changes. Its payload does not bind the displayed date to a bill ID or period key. The API's new relationship preflight reads the newer session/wallet for retry-resource tracking but keeps the old form payload. `domain/wallet.ts`, in `currentBill()` and `saveCard()`, chooses the billing period from `ctx.today` at save time.

User impact: A form opened in September overwrites October's due date after midnight. For statement day 5, due day 10, and next-month repayment, a September form displays October 10. On October 1, changing only its nickname sends that same date to the October bill, whose normal due date is November 10. October 10 passes the new bill's statement-date validation and silently shortens its due date by a month.

Remote confirmation: The reviewer kept a September 30 Card Edit form mounted, advanced only browser time to October 1, changed the nickname, and saved through the normal UI. The command still included `dueOn: 2026-10-10` with a September form month. The actual API preflight read an October bill due November 10. The service then changed that October bill to October 10 and wrote a matching `bill.updated` audit. The wallet displayed both September and October bills due October 10. The second case in `.qa-native/prototype/candidate-r9/r10-card-date-repro.json` records the payload, preflight result, before/after bill IDs/dates, and audit. The round reviewer read these checkpoints and inspected `r10-card-date-stale-form-september-date.png` and `r10-card-date-nickname-save-rewrites-october-bill.png`.

Recommendation and acceptance: Bind corrections to the period actually read, or require an explicit rebase decision with retained input when the period changes. Keep transaction, ownership, existing-bill snapshots, and intentional current-period correction behavior intact. Retest the exact open-form rollover, both months' dates/audits, shared-to-independent transitions, changed account relationships, and genuine current-period corrections. This is distinct from R10-02 because the save succeeds and changes the wrong bill.

### R10-04 — P2: Treat each new subscription consent as a new event

Source mechanism: `requestReminder()` obtains a fresh `wx.requestSubscribeMessage` result each time the user clicks its action, then calls `reminder.authorize` with the same kind/entity/template/accepted payload. That action has neither a new consent-event namespace nor a resource completion rule that distinguishes it from an earlier network-error retry. The service adds one grant per accepted authorization and the worker consumes those grants.

User impact: If an authorization committed but its response was lost, a later independent WeChat consent replays the old request result. After the old grant is consumed, the user sees successful authorization feedback for the second consent while no new grant is available for the next matching reminder.

Remote confirmation: `.qa-native/prototype/candidate-r9/r10-reminder-repro.json` records the real `requestReminder`, API client, transactional MemoryStore/service, and reminder worker, with mocked native consent, cloud transport and sender. The first accepted event committed one grant and lost its response; the dummy worker consumed that grant. The second separate accepted callback reused the identical request ID, returned true, and showed successful subscription feedback, but the grant remained zero. The next matching job became `needs_authorization` with `SUBSCRIPTION_REQUIRED`. A control with a distinct ID added a grant and allowed the waiting job through the dummy sender. Source hashes and the exact boundaries are in the JSON, which the reviewer read. No real WeChat consent, cloud account, or message delivery was used.

Recommendation and acceptance: New consent events need distinct identities, while retries registering the same consent retain idempotency. Preserve independent concurrent events, same-event replay before/after consumption, rejection statuses, platform failure, demo mode, and missing-template behavior. The implementation author's separate `docs/ux-loop-reminder-consent.md` records an old-code red run and corrected 7 consent tests, with 67 related tests passing remotely; that is correction evidence distinct from the old-source reproduction above. Final integrated API and full verification remain part of the next candidate's gate.

### R10-05 — P2: Prevent a delayed card picker from colliding with a newer guide sheet

Source mechanism: Detail's `prepareAction()` sets `busy` and waits for `wallet.get`, but its read-only guide entrance remains available. Opening the guide during that wait does not invalidate the card request. The response subsequently sets `showCards: true` without closing or deferring the guide. The guide is later in the template and remains the foreground sheet, but its newly added `guideContextVisible()` rejects all image operations while `showCards` is true.

User impact: A visible image button in the foreground guide becomes a silent no-op after the unrelated wallet response opens another sheet behind it. The sheets' visual ownership and controller ownership disagree.

Remote confirmation: The reviewer deferred `wallet.get`, used the rendered Join action, and opened the guide while the request was pending. After release, both `showCards` and `showGuide` were true; the foreground/focused sheet was the guide. Clicking its image ran `previewImage` but performed no image-URL request, no native preview, and no toast. `.qa-native/prototype/candidate-r9/r10-overlapping-sheet-repro.json` records the DOM focus/front-sheet and controller/API state. The round reviewer read it and inspected `r10-overlapping-sheet-guide-before-wallet.png` and `r10-overlapping-sheet-image-click-ignored.png`.

Recommendation and acceptance: Coordinate sheet ownership or invalidate a superseded picker request so only the appropriate operation is active. Preserve useful read-only access and the earlier protection against late previews after guide dismissal. Repeat delayed picker success/failure, open/close/reopen guide or rules, and an ordinary matching-card selection. A foreground action must remain usable and obsolete requests must not open hidden extra sheets.
