## Confirmed finding

### R22-01 — P3: Keep a retired concurrent-edit simulation from replacing the new scenario's feedback

Source mechanism: `prototype/runtime.js` captures the current form in `simulateConcurrentEdit()`, checks its ownership before and after reading the latest participation, and then awaits the real simulated concurrent command. After that command returns, it unconditionally writes a workbench message instructing the user to save and expect a version conflict. It does not check whether another page/scenario has become current during that final await.

The independent remote proof opens Progress through real source/workbench controls, edits its unsaved value to 3, and starts the visible concurrent-edit simulation. The actual `participation.progress` command preserves the stored progress of 2 while advancing the version from 2 to 3; its successful response is held after commit. The user then selects the Review scenario, accepts the real leave confirmation and reaches a ready moderator Review page with its correct explanatory feedback. Releasing the unchanged old response replaces that new feedback with the old form's version-conflict instructions.

The consequence is deliberately bounded. The new Review instance, route/hash, stack, role and serialized page data remain unchanged. The old Progress input remains 3 and dirty. Command count is exactly three before and after response release: the one committed simulation and the two intentional Review fixture submissions. The stored participation remains at progress 2 and version 3. There is no continued stale write, data loss, role mutation or native authorization bypass. The visible error is an unrelated instruction presented as the current workbench next step.

Evidence: `.qa-native/prototype/r22-before/r22-concurrent-feedback-report.json`, its QA reproduction, captured current/frozen functions and canonical AST. The lead read the complete command/result chronology, actual leave prompt, old and new feedback, state/role comparisons, persisted record and function-comparison limitations, then inspected all four screenshots: `r22-concurrent-feedback-real-leave-confirmation.png`, `r22-concurrent-feedback-new-review-before-release.png`, `r22-concurrent-feedback-old-message-overwrites-review.png` and `r22-concurrent-feedback-stale-message.png`. The proof records zero runtime exceptions. It invokes no hidden business handler and injects neither actor nor draft state.

Recommendation: Check the captured operation/page ownership after the final command and before publishing its successful workbench feedback. A retired operation should preserve the command that already committed while leaving the newer scenario's explanation intact. Keep current-form simulation, visible version-conflict recovery and actual service/version assertions working.

Acceptance: Hold a genuine simulation response after commit, complete a different visible scenario, and release it. The new scenario's feedback, page, role and input must remain unchanged and no later command should be issued. In the uninterrupted control, the simulation must still show accurate guidance and the original form must reach the real version-conflict/reload/reapply flow. This finding and regression concern a successful committed response and persistent workbench guidance. A delayed rejection from the outer control handler was not separately demonstrated or tested; the correction is not described as suppressing every asynchronous error toast.
