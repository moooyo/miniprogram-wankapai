# Core UX review and remediation

## Scope and method

The initial source review covered activities, detail, wallet, card editing, todo, progress, receipt, rewards, and participation history. The implementation ownership in this change covers activities, detail, card editing, progress, receipt, history, and the shared navigation helper. Wallet, todo, rewards, shared styles, and sheet internals are integrated by the other workstreams.

The review follows UI UX Pro Max priorities for error recovery, state preservation, touch interaction, accessible forms, and predictable navigation. Source review is not a substitute for actual device or cloud acceptance. No local tests, builds, runtime probes, or validation suites were executed by this workstream. Remote verification is coordinated by the root task.

## Additional findings during implementation

- The activity list used cashback-specific completed/received labels for discount benefits. It now uses `benefitCopy`, preserving the distinction between a bank payment and an already enjoyed discount.
- The new-activity subscription action had no request feedback or duplicate-click guard. It now exposes a busy state and disables repeated requests.
- Bank choices in the expanded picker did not expose selection state. They now expose the same pressed semantics as the visible bank rail.
- Detail reads could complete out of order, including secondary image/card-name reads. A request sequence now prevents older data from replacing the current activity context.
- A naive navigation fallback could replace a user-canceled normal back operation. The helper checks the navigation stack first and leaves ordinary back cancellation intact.

## Round 3 findings: refresh continuity and loaded windows

The todo controller previously reused the initial loading branch after every mutation and page return. This unmounted a long list, removed its priority groups, and replaced previously read records with an error on a refresh failure. Initial loading and refresh are now distinct. Existing tasks and groups remain mounted during refresh. A failed refresh preserves the prior snapshot, labels it as previously read data, and offers a direct retry. Row actions, edit navigation, completion, skip/resume, and undo are blocked while refreshing or outdated. A successful retry clears that restriction. Mutation success is reported before refresh, and a later refresh failure explicitly preserves the saved-action notice instead of implying that the write failed. Request versions and unload checks exclude obsolete responses and obsolete error feedback.

Activities and history also reset their loaded extent to the first 20 or 30 rows after a detail-page return. A refresh with unchanged filters now requests enough pages to rebuild the previously loaded unique-row count, checking request identity after each await and merging by stable ID. The old rows and cursor remain intact until the complete refresh succeeds. Any intermediate failure retains the complete old window. Only an actual filter change clears the rows; reselecting the current filter does not reset the window.

`tests/ux-loop-todo.test.ts` covers refresh continuity, stale-action locking and recovery, successful mutations followed by failed refreshes, and request races. Additional cases in `tests/ux-loop-core.test.ts` cover opening a second-page item and returning, changed second-page content, partial refresh failure, and filter changes while a later refresh page remains in flight. Remote validation remains coordinated by the root task.

## Round 5 findings: detail refresh and registration conflicts

A persistent refresh notice identifies outdated content and offers retry. Primary actions, management mutations, progress/receipt editing, card selection and confirmation, expected-date editing, and reminder authorization are blocked both in handlers and in disabled control states until a successful refresh. Late reads and stale confirmation/card-picker responses cannot replace or operate on a newer record. A successful mutation remains acknowledged if the subsequent read fails; retry only reads again. A dirty expected-date selection survives refresh, displays a changed stored date, and cannot be saved against a record that is no longer awaiting receipt confirmation.

Progress conflict summaries now state the server's registration status as well as progress and participation stage. The comparison explicitly identifies the retained local inputs. Optional registration controls remain visible when retained input or a restored draft differs from the current server record, including a locally checked registration that the server has canceled. The user can inspect and edit the checkbox before an explicit reapplication; no automatic merge occurs and expected-version protection remains intact.

Four form regressions cover registration-only conflicts in both directions and both directions of draft/server registration differences, including explicit saves with the refreshed version.

### Explicit intent for new-card creation

New-card forms now own a generated creation intent. It is persisted as draft metadata and passed through the optional `api.command` intent option only for `card.save` requests without an existing card ID. Editing an existing card retains the normal resource-based command behavior. Input comparison and draft baseline versions exclude the intent metadata, so a freshly generated key cannot falsely imply that the user's card fields changed.

A new form always receives a new key. A valid saved key is reused only after the user confirms draft recovery; declining recovery retains the fresh key, and confirmed legacy or invalid-key drafts keep their fields while receiving a fresh key. Before the first creation request, the form persists the intent even when no default field was edited. A pending creation draft is therefore recoverable after an ambiguous response and is not removed merely because its field values equal the baseline. Retries in the same form keep the same intent, while successful cleanup remains conditional on the captured draft revision and never transfers the old intent to a new form.

`tests/card-creation-intent.test.ts` exercises real controller boundaries for new forms, explicit recovery or rejection, legacy and invalid metadata, unchanged default forms, ambiguous-response retry, successful cleanup, and existing-card edits. It also separates an earlier ambiguous creation of card A from an explicit later fresh creation of A after the existing card was edited to B. API/service replay semantics are verified in the API workstream; this controller change adds no domain fields or relaxed validation.

An additional recovery boundary is handled when the server accepted a card but its response was lost: the refreshed wallet can contain the card created by that still-pending intent. Before sending, the controller now records an explicit pending marker, its intent key, and the exact normalized command payload signature. After confirmed recovery, only that same pending intent with a byte-for-byte identical normalized payload may bypass the client nickname collision caused by its possible prior creation. A key alone, a legacy draft, a mismatched signature, a different intent, or a modified payload grants no exemption. All other field and server validation remains unchanged. Successful completion removes the pending evidence; a definitive non-network failure clears it, with revision checks preventing a late failure from overwriting a newer draft.

The creation regression suite also runs the real controller through the real API transport and `createService`, simulating acceptance followed by response loss, reading the created card back in the wallet, confirming draft recovery, and replaying the original request ID without creating a second card. Modified-payload, legacy/no-evidence, and definite-failure cases preserve ordinary nickname validation.

## Round 12 findings: unresolved creation periods

### Legacy card creation is lookup-only

A pending legacy card payload that contains an actual billing date without a bill or period target can no longer be submitted as a fresh mutation. A period-bound pending creation whose original period has ended also uses result lookup only. Before retrying a pending billing creation, the controller reads the current server period, including when the form stayed open across midnight. The form locks its fields in lookup-only mode and offers an explicit result lookup and a wallet-check action. The lookup sends the original payload and intent through `api.command` with `replayOnly`; the API uses the separate owned-ledger `request.replay` query, which fails closed on older backends. No query failure, including an unknown-action response, is converted into a write or interpreted as proof that an earlier in-flight request can never commit.

An unresolved result retains the original draft and explains that the prior operation may still complete. Recovery confirmation describes the recorded billing period and the uncertain result before the user decides; discarding a local draft is explicitly distinguished from canceling an already dispatched operation. A later lookup can recover an original-period success without creating or correcting any current-period bill. Matching resolved drafts are removed only under their captured revision; unrelated edited draft content and newer draft revisions remain protected. Normal current-protocol creations still retry their original payload and intent while the original period remains current, including when the previous request never reached the server.

### Receipt drafts carry an explicit activity target

Fresh server dates determine the current period. Same-period uncertain requests can safely continue their original creation; crossed-period, missing-target, unavailable-activity, or changed-context requests use owned-ledger result lookup only. Lookup misses and failures retain the original evidence and never trigger a fresh write. Inputs remain locked while resolving that original operation.

Recovery prompts identify the original period and actual receipt date before the user decides, and explain that the service may already have saved the record. Declining pending recovery retains the draft and prevents new input from silently replacing it. A normal draft from another or unknown period requires explicit target confirmation before editing or saving; actual receipt dates are never used to infer the participation period. Targeted drafts are filtered by activity, scope, card, period, and known participation identity rather than being automatically migrated to a newly found current record.

Explicit historical receipt routes ignore unrelated modern drafts and do not automatically recover an unassigned legacy creation draft. The legacy draft remains untouched. Existing participation edits continue to use their original snapshot, receipt-date range, and expected version. Conditional draft migration and cleanup preserve newer revisions, and failed storage prevents dispatch of a new creation whose retry identity could not be persisted. Closed-page responses cannot navigate a replacement page. ## Round 21 finding: detail reminder preference prerequisites

Detail previously allowed a native subscription request while the corresponding deadline or expected-reward preference was disabled. The authorization grant was correctly recorded, but the reminder worker correctly suppressed delivery. The entry point did not explain the separate disabled prerequisite or provide a settings route.

Before a production request, detail now reads a fresh session and the relevant reminder preference. A disabled preference presents a specific explanation and an optional route to reminder settings. The user must save that setting and return to the participation to request its limited native authorization; the app does not enable preferences automatically. Canceling the explanation leaves the participation and grants unchanged. A failed preference read remains an inline, retryable state and explicitly states that native authorization has not been requested. Demo mode keeps its existing no-send explanation.

Preference preparation is scoped to the current page, visibility generation, detail read generation, participation identity, stage, and expected date. Hiding or unloading before authorization cancels the preparation and releases only its own busy state. Late preference responses and modal decisions cannot request consent or navigate another page.
